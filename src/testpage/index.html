SimpleTrans Translation Test Page

A fixed English fixture for manual translation checks. The text, order, and structure stay the same, so a failed check can be repeated against the same page.

This page is bundled with the extension. It loads the page-injection runtime itself because Chrome does not inject content scripts into extension pages. The control bar above is part of the test harness and is excluded from translation.

Fixture version 1 · No network resources · English body · Last reviewed 2026-11-16

Overview

The fixture is deliberately ordinary. It looks like a small documentation page, not a product screen, because the goal is to observe translation behavior rather than to test a visual design.

Every block below is visible on load. There are no cookie banners, no recommendation feeds, no login prompts, and no lazy-loaded cards that could change the paragraph count between two runs.

Typography

Inline formatting

Good translation tests need strong emphasis, subtle emphasis, small print, highlighted terms, and an API label. Inline code such as npm run build should survive as code, while a link to the Lists section stays a link.

Chemical notation like H2O and a footnote marker1 test subscript and superscript. A long sentence with a bold phrase that contains nested emphasis checks that nested inline tags are not split into unrelated fragments.

A second paragraph checks wrapping at different widths. Translation should keep the sentence readable, preserve the inline order, and avoid adding extra blank lines around the inserted text.

Long Article

The sections below provide enough text to scroll, batch, and compare viewport-first scheduling. They are intentionally repetitive in structure and varied in vocabulary.

Why a fixed fixture matters

A translation check is only useful when the input is predictable. When the source page changes between runs, a new heading, a cookie banner, or a lazy-loaded card can alter paragraph counts and make a regression look like a formatting bug. A fixed fixture removes that noise.

The page is intentionally plain. It uses system fonts, local CSS, and no images, so a missing translation cannot be confused with a failed network request. Every block is visible on load, and every section has a stable identifier.

What the fixture covers

The fixture covers block and inline text. Headings, list items, table cells, and paragraphs behave as block hosts; emphasized phrases, code, links, and superscripts live inside them. A translation that appears in the wrong host is easy to see here.

Form controls are included as deliberate negative cases. Their labels are ordinary text and should translate. Values, placeholders, and option labels are control state, not page copy, so they should stay in English.

Reading the results

Numbers and punctuation are part of the copy. Dates, prices, percentages, phone numbers, and URLs should keep their shape while the surrounding sentence is translated. Quotes and dashes should not acquire stray spaces or turn into different characters.

The long article provides scroll and batching coverage. A whole-page run should start with paragraphs near the viewport and continue as the reader scrolls; repeating the run should not create duplicate translations for the same host.

Repeating a failed check

A failed check should be repeatable. The fixture keeps its section identifiers, paragraph order, and headings stable, so a tester can return to the same block and compare the same host. If the cache makes a second run instant, clear the cache before testing a fresh request.

The page does not try to force a cache miss. Caching is a product feature, and the fixture should show both states honestly: a cached result may appear immediately, while a fresh result shows the loading and streaming phases.

Keeping the fixture honest

When the fixture changes, the change should be deliberate. New copy belongs in a new section or a reviewed replacement, not in a random edit that silently changes the baseline. The section identifiers are part of the test contract.

Finally, keep the fixture close to the product. It loads the same page-injection entry as a normal page and uses the same task, renderer, and cache; only the trigger differs. That is why the page is a useful manual check rather than a separate mock.
