## 1. 职责与边界

- 接收 `st-gateway` 端口上的数据面消息与页面注入的统一段落提交（`ST_PAGE_SUBMIT`），返回增量、定稿与终态。
- 页面提交路径：按 `tabId` 找到页面连接，按 `requestId` 建立提交；读取设置、实例与密钥，一次预取缓存并立即回显命中项，未命中项按唯一 key 分组、按实例参数切批，交给临时执行器逐 group 翻译，结果逐段回帧。
- 数据面路径：保留 `ST_TRANSLATE_BATCH`（协议兼容与测试），负责载荷校验、全局并发、每连接在途批次、取消、断线与批超时。
- 负责按段的缓存查询与命中结算，并在成功定稿后写缓存；缓存结构、容量与淘汰由 A4 负责。
- **不保存任务状态**：批次表、提交表、在途共享表、控制器与计时器只在当前 Service Worker 事件循环的内存里；不写 `storage`、不做恢复。
- 不重试、不切备用（P9）；不做队列调度与 JSONL 批量编码（P6.4）；`ST_TEST_ENGINE` 不进入提交、批次计划与在途复用，也不读写缓存。

## 2. 连接与心跳

- 只接受端口名 `st-gateway`、发送方 `sender.id === chrome.runtime.id` 的端口；其它端口直接断开。
- 每个端口维护 `{ port, tabId, batches, submissions, disconnected, logConfigSent }`。
- `handleConnect` 按 `sender.tab.id` 把连接登记到 `tabConnections`；同一标签页建立新连接时记 `gateway.replace` 并清理旧连接，断开时同步删除。`findConnectionByTab(tabId)` 供一次性提交按 `tabId` 找连接。
- `ST_PING` 立即回 `ST_PONG { sentAt, receivedAt }`，不进入批次表、不占并发名额、不写存储。
- 每个连接首个 `ST_PING` 后，若 `logConfigSent` 为假，先置为真，再异步读取设置并补发一帧 `ST_LOG_CONFIG { level }`；每连接只发一次，重连后的新连接重新下发。读取失败时用当前缓存级别（默认 `info`），不因下发失败断开连接；不做级别变更推送。
- 端口 `onDisconnect` 或 `ST_CLOSE`：中止该端口全部在途上游请求、清理批次表、提交表与在途订阅；断线后不发帧。

## 3. 页面提交与批次处理

### 3.1 提交入口

```text
page (D5) --ST_PAGE_SUBMIT--> A1.receivePageSubmit
  形状校验（scope / requestId / 段落 / hostId / 禁止字段）
  → sender.tab.id → findConnectionByTab
      找不到：返回 { ok: false, error: { code: NETWORK, reason: NOT_CONNECTED } }「页面通道未连接，请刷新后重试」
  → acceptPageSubmit({ requestId, traceId, scope, targetLang, domain, viewport, paragraphs, tabId })
  → 初始化、缓存预取与命中回显后返回 { ok: true, data: { accepted: true, requestId, scope, paragraphs, chars } }；未命中翻译异步执行
A2.acceptPageSubmit:
  → 按 tabId 找连接、检查 requestId 重复
  → 分流：text.length > MAX_SEGMENT_CHARS 的 item 记为超长，不进入分组、切批与缓存
  → 读取设置 / 实例 / 密钥 / 目标语言
  → 为其余段落计算 key → 一次 getMany
  → 创建提交；超长段逐段 ITEM_ERROR(TEXT_TOO_LONG)
  → 命中：逐段 START → DONE
  → 未命中：唯一 key 分组 → 切批 → 临时执行器逐 group translate
  → 全部 item 结算后 BATCH_DONE + batch.done
```

```js
// router.js
receivePageSubmit(payload, sender, traceId)
  → { ok: true, data: { accepted, requestId, scope, paragraphs, chars } }
  | { ok: false, error }

// gateway.js
acceptPageSubmit({ requestId, traceId, scope, targetLang, domain, viewport, paragraphs, tabId })
  → { accepted: true }
  | { accepted: false, error }
```

- `acceptPageSubmit` 的参数：`requestId`（页面生成的 `s-…`）、`traceId`、`scope`（`page` / `single`，只影响日志与校验，不改变分组与切批）、`targetLang`（缺省读设置）、`domain`（页面 hostname）、`viewport`（只随提交透传，当前不参与缓存、分组与切批）、`paragraphs`（`{ hostId?, text }`，按页面顺序）、`tabId`（结果帧路由键）。
- A1 只做形状校验、计数与回执，不查缓存、不调用引擎；A2 初始化失败时 A1 仍返回 `accepted: true`，失败通过逐段 `ST_ITEM_ERROR` + `ST_BATCH_DONE(ok:false)` 表达。
- 同一连接内 `requestId` 重复时拒绝（`DUPLICATE_REQUEST`），避免结果串台；提交结束、连接清理后同一 `requestId` 可复用。无 `requestId` 的匿名提交使用内部键 `anon-N` 登记、不参与重复判定；页面始终生成 `s-…`，匿名路径只用于兼容与测试。
- A1 等到 A2 完成初始化、一次缓存预取与命中回显后回执；未命中项的分组、切批与翻译异步执行，不等待翻译完成。
- 初始化失败（读取设置失败、扩展停用、目标语言不支持、无可用实例、实例无效、读取实例失败、缺密钥）逐段发 `ST_ITEM_ERROR(code, message)`，再发 `ST_BATCH_DONE { ok: false, failed: 段落数 }`；不能只发 `BATCH_DONE`，否则页面停在「已提交」。key 计算与缓存读取失败只降级处理，不算初始化失败。
- 缓存命中帧可能早于 `ST_PAGE_SUBMIT` 的回执到达；D5 发送前先登记临时提交记录（状态 `submitting`），命中帧可直接按 `requestId + itemId` 路由；提交失败时 D5 把未结算段落标错并清理临时记录。
- 页面提交按 `requestId` 去重，不计入数据面每端口 4 批的在途额度。
- 提交创建时启动 180 秒超时（`AI_TIMEOUT_MS.batchTotal`），早于 A1 回执返回；P6.4 的队列等待计入该超时。
- 数据面 `ST_TRANSLATE_BATCH` 路径保留给协议兼容与测试，页面不走该路径；结果主路径是 `ST_PAGE_SUBMIT`。
- `ST_CANCEL_BATCH` / `ST_CANCEL_ITEM` 由 A2 支持，页面暂不发送，真实取消在 P7 接入。

### 3.2 缓存预取与命中回显

- 缓存开关取 `settings.cacheEnabled`（缺省为开）。缓存关闭时仍计算 key 用于同 key 分组与在途复用，但不读、不写 IDB，命中数为 0。
- key 由 A4 `buildCacheKey` 计算：`promptHash` 每次提交只算一次，`reasoningEffort`、`batchEncodingVersion`、`promptVersion` 来自实例与常量，`context` 为空串。
- 提示词哈希或任一段 key 计算失败：本次提交不参与缓存，分组键回退为 `fallback:<text>`，记 `cache.error`，翻译继续。
- 读取：全部唯一 key 在一个只读事务中 `getMany`；唯一 key 为空时不查缓存；读取异常按全部未命中处理，写缓存仍尝试，记 `cache.error`。
- 命中 group：为组内每个 item 发 `ST_ITEM_START` → `ST_ITEM_DONE(text)`；`usage` 为 `null`；`cacheHits` 按原始 item 累计；不占执行器名额；不重复写缓存。
- 命中项按页面顺序回帧，允许与未命中项的 `START` / `DONE` 交错。
- 命中仍要求已配置可用密钥：缓存读取在设置、实例与密钥检查之后。
- 提交创建时捕获 A4 generation；写入时 generation 不一致则跳过（沿用 P5）。
- 命中不更新条目的 `text`；`meta.lastUsedAt` 由 A4 `getMany` 的既有节流逻辑处理；key 版本仍为 P6.2 的 `cache:v2:`。

### 3.3 唯一 key 分组与切批

```text
acceptPageSubmit:
  按 tabId 找连接 / 检查 requestId 重复
  → 分流超长段（text.length > MAX_SEGMENT_CHARS，直接失败、不进入分组）
  → 读取设置 / 实例 / 密钥 / 目标语言
  → 为其余段落计算 key（缓存关闭也计算，用于去重）
  → 按 groupKey 分组（同 key 的段落合并为一个 group）
  → cacheEnabled ? getMany(uniqueKeys) : 全部未命中
  → 超长段逐段 ITEM_ERROR(TEXT_TOO_LONG)
  → 命中 group 逐段回显
  → 未命中 group：已在途的订阅，其余进入 newGroups
  → splitBatches(newGroups, { batchSize, batchMaxChars })
  → 临时执行器逐 group 执行
  → 全部 item 结算后 BATCH_DONE + batch.done
```

- 分组键是 `cacheKey`；key 失败时是 `fallback:<text>`。`group.text` 取第一个 item 的文本；同 key 的原文、模型、语言、思考强度与提示词一致。
- 分组不改变页面 `itemId`：`hostId` 兼作结果帧 `itemId`，缺失时用 `p-<index>` 占位；每个原始段落仍各自结算与计数。
- 单段超过 `MAX_SEGMENT_CHARS`（4000）的段落不进入分组、切批与缓存，提交创建后逐段以 `TEXT_TOO_LONG` 失败；其余段落继续，提交按部分成功处理。未超过 4000 但超过 `batchMaxChars` 的 group 单独成批并标记 `oversize`。
- `cacheEnabled` 只控制缓存读写，不控制分组与切批。
- 同提交内同 key 的段落合并到一个 group：`dedupeHits += group.items.length - 1`，记 `dedupe.merge`；同一 group 只执行一次上游，`done` / `failed` / `cancelled` 仍按原始 item 计数。
- 切批参数取实例值：`batchSize` 默认 8、正整数、不设业务上限；`batchMaxChars` 默认 1000、不设固定上下限。缺失或非法时归一为默认值。
- 两个限制同时生效、先到先切：`batchSize` 限制 group 数，`batchMaxChars` 限制组内原文 `text.length` 之和；以 group 为单位切分，绝不拆段；空批次不产生。

```js
function splitBatches(groups, { batchSize, batchMaxChars }) {
  const batches = [];
  let current = [];
  let chars = 0;

  const flush = () => {
    if (current.length === 0) return;
    batches.push({
      groups: current,
      chars,
      oversize: current.some((group) => group.text.length > batchMaxChars),
      state: 'pending',
    });
    current = [];
    chars = 0;
  };

  for (const group of groups) {
    const length = group.text.length;
    if (current.length > 0 && (current.length >= batchSize || chars + length > batchMaxChars)) flush();
    current.push(group);
    chars += length;
    if (current.length >= batchSize) flush();
  }
  flush();
  return batches;
}
```

- `oversize` 只用于 `batch.plan` 的 `oversizeBatches` 计数，不改变执行方式；超长段单独成批后仍按单段请求执行。
- 批次顺序与页面提交顺序一致；P6.3 不做视口优先重排。
- 例：20 个不同文本的段落、每段 100 字符、`batchSize=8`、`batchMaxChars=1000` → 3 批（8 / 8 / 4 组，800 / 800 / 400 字符）；`batchMaxChars=300` → 每批 3 组、300 字符（末批 2 组、200 字符）；其中一段 3000 字符 → 单独一批，`oversize=true`。
- 协议硬上限 `MAX_BATCH_ITEMS=12`、`MAX_BATCH_CHARS=12000` 只用于数据面 `ST_TRANSLATE_BATCH` 校验；页面提交的内部批次由实例参数控制，可能超过 12000 字符，`batchChars` 记入 `batch.plan` 便于发现过大批次。

```js
group = {
  key, cacheKey, text,
  items: [],           // 同 key 的原始 item
  cacheEntry: null,
  shared: null,        // 在途共享执行；P6.3 为单段 shared，P6.4 为批次 job
  state: 'pending',    // pending / cache-hit / owner / subscribed
};

batch = {
  groups, chars, oversize,
  state: 'pending',    // pending / running / done
};
```

- `batch` 不进入页面帧，只用于日志与 P6.4 队列；P6.4 把每个 batch 映射为队列 job。

### 3.4 在途复用与临时执行器

```js
shared = {
  key, cacheKey, text,
  targetLang, instance, apiKey, limit,
  cacheEnabled, cacheGeneration, domain,
  controller: AbortController,
  subscribers: Set<{ submission, item }>,
  owner: { submission, item } | null,   // 只负责增量与 usage 归属
  state: 'running' | 'done' | 'failed' | 'cancelled',
  startedAt,
  ownerSubmission,
};
```

```text
for batch of batches:
  for group of batch.groups:
    if group 已全部结算: continue
    shared = inFlightByKey.get(group.key)
    if shared: 订阅（dedupeJoined）；记 dedupe.join；continue
    shared = createShared(group); 订阅并记 owner；记 dedupe.owner
    void runShared(shared)
```

- `inFlightByKey` 以 group 键索引，同一个 key 在当前 Service Worker 内存里只保留一个 `shared`；跨提交、跨连接复用。
- 订阅：为 group 内每个 item 发 `ST_ITEM_START`，把 `{ submission, item }` 加入 `shared.subscribers`；创建者组的第一个订阅者成为 `owner`。跨提交订阅按 item 累计 `dedupeJoined`，创建 shared 的提交累计 `dedupeShared`。
- `runShared` 在实例 `maxConcurrency` 名额内执行一次单段 `translate({ text, targetLang, instance, signal })`；`ST_ITEM_DELTA` 只发给 `owner` 的 item，其它订阅者不发增量、直接等定稿。
- 成功：从 `inFlightByKey` 删除，`state = 'done'`；对当前全部订阅者发 `ST_ITEM_DONE(text)`，`owner` 带上游 `usage`，其余为 `null`；随后按 group 写一次缓存（key、text、generation、domain），写失败只记日志。
- 失败：从 `inFlightByKey` 删除，`state = 'failed'`，记 `dedupe.error`（warn）；对全部订阅者发 `ST_ITEM_ERROR(code, message)`；不写缓存。
- 取消：订阅者只从 `shared.subscribers` 移除；集合为空时置 `cancelled`、abort 控制器、删除在途表并记 `dedupe.abort`；仍有其它订阅者时继续执行。
- owner 退出：`owner` 置空，结果仍 fan-out 给剩余订阅者，`usage` 全部为 `null`，不影响执行。
- 连接断开：移除该连接的全部订阅；若无订阅者则 abort 并删除在途表。
- 提交超时：只移除本提交的订阅并以 `NETWORK / BATCH_TIMEOUT` 结算；shared 仍有其它订阅者时继续执行。
- 缓存关闭：仍创建 shared、仍 fan-out，但不读写缓存；key 使用 `fallback:<text>` 时同样不读写缓存，跨提交共享只按同文本成立。
- 临时执行器逐 group 单独调用，不按批次串行阻塞其它批次；并发名额来自实例 `maxConcurrency`，与 P6.4 队列语义衔接。

### 3.5 取消、超时与断线

| 操作 | 排队中 / 未开始 | 共享执行中 | 已结算 |
| ---- | --------------- | ---------- | ------ |
| `ST_CANCEL_ITEM` | 摘除订阅，标记取消，不发帧 | 从 `shared.subscribers` 移除该订阅；集合为空则 abort、删除在途表、记 `dedupe.abort`；页面已移除显示，不补发取消帧 | 忽略 |
| `ST_CANCEL_BATCH` | 取消该提交全部未结算 item，不发帧 | 逐个摘除订阅，无订阅的 shared abort | 保留；全部结算后发 `ST_BATCH_DONE` |
| 提交超时（180 秒） | 未结算 item 以 `NETWORK / BATCH_TIMEOUT` 失败并发 `ST_ITEM_ERROR` | 同上，摘除订阅；shared 仍有其它订阅则继续 | 保留 |
| 端口断开 | 该连接全部提交标记结束、清理订阅，不发帧 | 无订阅的 shared abort | 保留 |
| 同一标签页新连接覆盖旧连接 | 旧连接按断开处理 | 同上 | 保留 |

- 取消、超时与断线只影响本提交/本连接的订阅，不影响其它提交与连接；shared 仍有订阅者时继续执行。
- 已结算 item 的迟到帧忽略；页面发起的取消已经在页面移除显示，因此不补发 `CANCELLED` 帧。
- 页面暂不发送 `ST_CANCEL_BATCH` / `ST_CANCEL_ITEM`，真实取消在 P7 接入。

### 3.6 计数

| 计数 | 口径 |
| ---- | ---- |
| `done` / `failed` / `cancelled` | 按原始 item 计；同 key 合并后的 group 不改变该口径 |
| `cacheHits` | 命中缓存的原始 item 数（按 item 回帧时累计） |
| `cacheMisses` | 未命中的 group 数（仅缓存启用且 key 计算成功时累计） |
| `cacheWrites` | 尝试写缓存的 group 数（创建 shared 的提交累计） |
| `dedupeHits` | 同提交内因同 key 合并而少执行的 item 数（`group.items.length - 1` 之和） |
| `dedupeShared` | 本提交创建 shared 的 group 数 |
| `dedupeJoined` | 本提交订阅其它在途 shared 的 item 数 |
| `uniqueGroups` | 本次提交的唯一 group 数 |
| `batches` | 切批后的批次数 |

计数随 `batch.done` 输出；超长段的失败计入 `failed`，因此发出 `ST_BATCH_DONE` 时 `done + failed + cancelled` 仍等于提交的原始段落数。

### 3.7 与 P6.4 的接口

- P6.4 把每个 batch 作为队列 job；`batch` 的 `groups` / `chars` / `oversize` / `state` 字段直接复用，`state` 由 `pending` → `running` → `done`。
- 一个 batch 只含 1 个 group 时走单段 `translate`；多个 group 时走一次批量请求（JSONL 编码），批量请求的对齐结果按 group 回填。
- `submission.groups`、`inFlightByKey`、`ST_ITEM_*` 帧与按 group 写缓存的语义保持不变；队列等待计入 180 秒提交超时。
- 队列并发仍取实例 `maxConcurrency`；P6.4 替换的是执行器与调度，不是提交入口、分组、切批与帧契约。

## 4. 数据面批次执行

`ST_TRANSLATE_BATCH` 保留给协议兼容与测试，页面不走该路径；本节的校验、并发与超时语义对该路径生效。

1. 校验（顺序见 [E1-消息协议](./E1-消息协议.md) 第 6 节）；任一失败只回一帧 `ST_BATCH_DONE { ok: false, error }`，不创建批次。
2. 读取设置、实例列表首个实例、密钥；没有实例、缺密钥或实例无效时整批 `CONFIG`。网关**不创建实例、不写存储**。
3. 缓存启用时先用实例提示词计算一次 `promptHash`，再逐段计算 key，并在一个只读事务中读取本批 key；命中结果随批次创建一起记录（见下文「缓存」）。
4. 创建批次并设置 180 秒批超时；批次内各段**逐段顺序**执行。
5. 每段：命中 → `ST_ITEM_START` → `ST_ITEM_DONE`；未命中 → 取全局名额 → `ST_ITEM_START` → `translate(item, signal)` → 转发 `ST_ITEM_DELTA` → `ST_ITEM_DONE` 或 `ST_ITEM_ERROR`；成功定稿后异步写缓存。
6. 全部段结算后回 `ST_BATCH_DONE { requestId, ok, done, failed, cancelled }`。

### 缓存

- 缓存开关取 `settings.cacheEnabled`（缺省为开）；关闭时**不做 key 计算、不读 IDB、不写 IDB**，行为等同全部未命中。
- key 由 A4 `buildCacheKey` 计算，输入为 key 版本、引擎类型、模型、`settings.sourceLang`、目标语言、A3 `PROMPT_VERSION`、A3 `BATCH_ENCODING_VERSION`、实例 `reasoningEffort`、实例提示词哈希、每段 `context` 与原文；提示词哈希或任一 key 计算失败 → 本批不参与缓存（全部未命中且不写），记 `cache.error`。
- 提示词哈希每个批次只算一次，不在每段重复计算；成功计算后以 `cache.key.version`（debug）记录当前 `CACHE_KEY_VERSION`，不记哈希。
- 读取用一个只读事务读本批全部 key；读取异常按全部未命中处理，仍尝试写入，记 `cache.error`。
- 命中段：发 `ST_ITEM_START` 与 `ST_ITEM_DONE`，`usage` 为 `null`，不发 `ST_ITEM_DELTA`，不占上游并发名额，不调用 A3。
- 未命中段：走原流程；`ST_ITEM_DONE` 发出后**异步**调用 A4 `set()`，写入失败只记日志，不改变该段结果。
- 只写「A3 成功且译文非空」的定稿；失败、取消、批超时、空译文一律不写。
- 批次携带 `domain`（页面 hostname），网关用 `normalizeDomain()` 归一；缺失、非字符串、超长或非法字符按空串处理，**不拒绝批次**。域名只写入未命中成功后的 `meta.domain`，不参与 key、不参与命中、不进入提示词与日志。
- 批次开始时捕获 A4 的 generation；用户清空缓存后，旧批次尚未完成的写入被跳过。
- 命中仍要求已配置可用密钥：缓存读取在校验、设置、实例与密钥检查之后，不改变缺密钥提示与整批拒绝语义。

### 并发

- 全局上游并发上限取当前实例 `maxConcurrency`（默认 4，正整数、不设固定上限）；信号量 FIFO。数据面按「段」获取名额，页面提交按「group」（一次单段 `translate`）获取名额。并发来源只有实例 `maxConcurrency`；`settings.concurrency` 仅作旧实例迁移回退。
- 每端口数据面在途批次 ≤ 4；超出立即 `TOO_MANY_INFLIGHT`，不在后台排队。页面提交不受该额度限制，只按 `requestId` 去重。
- 设置页测试翻译通过 `withUpstreamSlot(fn, limit)` 复用同一个信号量，不绕过上限。

### 取消

| 操作 | 排队中 | 执行中 | 已完成 |
| ---- | ------ | ------ | ------ |
| `ST_CANCEL_ITEM` | 标记取消，不发帧 | abort → `ST_ITEM_ERROR(CANCELLED)` | 忽略 |
| `ST_CANCEL_BATCH` | 全部标记取消，不发帧 | abort → 当前段 `ITEM_ERROR(CANCELLED)`，其余不结算 | 保留 |
| 端口断开 | 全部丢弃，不发帧 | abort，不发帧 | 保留（页面内存随页面销毁） |

取消是幂等的；取消后仍发一次 `ST_BATCH_DONE` 作为终态，`cancelled` 为未结算段数。

### 批超时

- 计时器在批次创建时启动，`AI_TIMEOUT_MS.batchTotal`（180 秒）。
- 到期：中止当前段，所有未结算段（含未开始的段）以 `ST_ITEM_ERROR(NETWORK, BATCH_TIMEOUT)` 结算，然后回 `ST_BATCH_DONE`。
- 未开始的段可能没有对应的 `ST_ITEM_START`，客户端按 `requestId`/`itemId` 结算。

## 5. 错误映射

| 场景 | 错误码 |
| ---- | ------ |
| 载荷/字段/语言/单段超长/在途超限/重复请求 | `OTHER`（单段超长为 `TEXT_TOO_LONG`） |
| 页面通道未连接 | `NETWORK`（`NOT_CONNECTED`） |
| 缺实例、缺密钥、实例无效 | `CONFIG` |
| 鉴权、额度（来自 A3） | `AUTH` |
| 限流（来自 A3） | `RATE_LIMIT` |
| 网络、超时、流中断、批超时 | `NETWORK` |
| 用户取消 | `CANCELLED` |

网关只回传错误，不执行重试、拆批与备用切换（P9）。

## 6. 日志

- 使用 E4（`src/shared/log/`），不直接调用 `console.*`；日志只输出控制台，不写存储。
- 连接与批次事件：`gateway.connect`、`gateway.replace`、`gateway.disconnect`、`batch.reject`、`batch.plan`、`batch.start`、`batch.done`、`item.error`、`item.cancel`。
- 缓存事件：`cache.hit`、`cache.miss`、`cache.write`、`cache.error`、`cache.key.version`。
- 去重事件：`dedupe.merge`、`dedupe.join`、`dedupe.owner`、`dedupe.abort`、`dedupe.error`。
- `batch.plan`（debug）：`requestId`、`items`（提交的全部段落，含超长失败项）、`groups` / `batches`（只统计未超长段落）、`batchSize`、`batchMaxChars`、`batchChars`、`oversizeBatches`、`cacheEnabled`、`cacheHits`、`cacheMisses`（后两者按 group 计）。
- `batch.start`（info）：`requestId`、`scope`、`items`（全部段落）、`batches`、`cacheHits`（按 group 计）。
- `batch.done`（info）：`done`、`failed`、`cancelled`、`cacheHits`、`cacheMisses`、`cacheWrites`、`dedupeHits`、`dedupeShared`、`dedupeJoined`、`uniqueGroups`、`batches`。
- `cache.hit`（debug）：`requestId`、`itemId`、字节数；`cache.miss`（debug）：`requestId`、组内 item 数；`cache.write`（debug）：`requestId`、字节数。`cache.key.version` 只记录版本号。
- `dedupe.merge` / `dedupe.join` / `dedupe.owner`（debug）：`requestId`、组内 item 数（`dedupe.owner` 另带订阅数）；`dedupe.abort`（debug）：`requestId`；`dedupe.error`（warn）：`requestId`、错误码、订阅数。
- `item.error`（warn）：`requestId`、`itemId`、错误码；`item.cancel`（debug）：`requestId`、`itemId`。
- 不记录页面正文、译文、上下文、域名、缓存 key 哈希、提示词哈希、提示词、密钥、请求头/体、完整 URL；批次被拒只记录 `reason` 与请求 ID。
- 日志失败不影响提交、切批、去重、缓存与错误码。

## 7. 边界情况

- 报文不是对象、类型未知、`payload` 缺失：回 `ST_BATCH_DONE`（`INVALID_MESSAGE`）。
- 数据面同端口在途批次重名：`DUPLICATE_REQUEST`；批次结束后同名可复用。页面提交按 `requestId` 去重，结束后同样可复用。
- 一个提交/批次失败不影响其它提交/批次；同一端口最多 4 个数据面在途批次。
- 端口发送失败（已断开）按断线处理，清理该端口并中止在途请求；页面提交的帧发送失败即视为该连接已断开。
- 网关不读取 `storage.session`，不写 `storage.local` / `storage.sync`；缓存只走 A4 的 IndexedDB。
- 命中或订阅时端口已断开：不发帧（该连接的提交已被清理）。
- 同 key 在途复用只在当前 Service Worker 内存中；SW 回收后同一文本可能再次调用上游。
- 旧页面（扩展更新前注入的内容脚本）可能不带 `domain`：按空串处理，不阻断翻译。
- 缓存命中帧可能早于提交回执：由 D5 的临时提交记录承接；提交失败时 D5 清理该记录。
- 页面提交初始化失败时逐段 `ST_ITEM_ERROR` 后再发 `ST_BATCH_DONE(ok:false)`，页面不会停在「已提交」。
- 切批以 group 为边界，不拆段；超长段单独成批，不丢弃。
